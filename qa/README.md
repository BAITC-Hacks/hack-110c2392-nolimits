# Приёмочное тестирование StockPilot

Проверяем бизнес-результат, ошибки импорта и жизненный цикл заказа. Код приложения не изменён. Тесты используют маленькие синтетические наборы с фиксированными датами, настоящее API через FastAPI TestClient и отдельную временную SQLite для каждого сценария. Они не обращаются к работающему серверу и не затрагивают базу коллег.

## Запуск

Из корня репозитория, Windows PowerShell:

```powershell
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
./.venv/Scripts/python.exe qa/run.py
```

Linux/macOS:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
.venv/bin/python qa/run.py
```

Повторно устанавливать окружение перед каждым прогоном не нужно. Проверить конкретный сценарий:

```powershell
./.venv/Scripts/python.exe qa/run.py -k E09
./.venv/Scripts/python.exe qa/run.py -k "A06 or A07"
```

Код выхода `0` означает, что выбранные проверки прошли. `1` означает обнаруженные несоответствия. Остальные коды pytest означают проблему выполнения/сбора тестов. Падающие проверки намеренно не скрыты через `xfail`: это приёмочные требования, а не обещание, что текущая версия уже им соответствует.

`qa/reports/` содержит JUnit XML, JSON с подробностями и Markdown со статусами. Каждый запуск фиксирует SHA, ветку, состояние рабочей копии, Python и ОС. Отчёты игнорируются Git; для команды сохранён отдельный [исходный отчёт](BASELINE.md).

## Что покрыто

| Группа | Проверки |
| --- | --- |
| E01–E07, E23–E24 | Ручной контроль формулы, остатки/поставки, поздняя поставка, нулевая потребность, MOQ и упаковка, изоляция складов, Lead Time, страховой коэффициент |
| E08–E13 | Stockout с нулевыми строками и без строк, пересечения периодов, пустые дни, изоляция складов |
| E14–E19 | Разовый заказ, дробление заказа клиента, корректность аудита, зимний пик, рост, перестановка строк |
| E20–E22 | Короткая/пустая история, конечность результатов, сохранность исходных данных |
| V01–V05 | NaN/Inf, отрицательные числа, нулевая упаковка, конфликтующие остатки, обратные даты, пустой артикул |
| A01–A08 | Запуск API, ошибочный импорт, сохранность данных, утверждение и перезапуск, ограничения итогового заказа |
| A09–A19 | CSV/XLSX, KPI, формулы в текстовых полях, повторное утверждение, график, русский CSV, устойчивость после плохого импорта, очистка старых периодов |

Дополнительно запускаются существующие `backend/tests` команды. Список ручных и ещё не автоматизированных сценариев: [ACCEPTANCE.md](ACCEPTANCE.md).

## Контрольная арифметика

84 дня стабильных продаж по 10 единиц. Lead Time = 10 дней, доступно 20, в пути 30 с прибытием на второй день, Safety Stock = 0, MOQ = 24, Pack = 12:

```text
Прогноз = 10 × 10 = 100
Чистая потребность = max(0, 100 − 20 − 30) = 50
Заказ = ceil(max(50, 24) / 12) × 12 = 60
```

Stockout с 1 по 16 марта включительно при стабильном спросе 10/день: восстановление ровно 160 единиц. Отсутствующие транзакции и явные нулевые строки должны давать одинаковую оценку. Исторические 160 единиц корректируют оценку спроса, а не автоматически добавляются целиком в новый заказ.

Для ручной загрузки через UI подготовить шесть наборов CSV:

```powershell
./.venv/Scripts/python.exe qa/make_fixtures.py
```

Результаты находятся в `qa/fixtures/`: базовый расчёт, увеличение inbound, stockout без транзакций, разовая закупка 4800, поздняя поставка, неправильный остаток. Каждый набор содержит `expected.json` с датой среза, количеством строк и ожидаемым результатом. Для первого набора загрузить все пять таблиц, включая пустую таблицу stockouts с заголовками. Пустой файл должен очищать старые периоды, а не оставлять их от предыдущего demo. Наборы синтетические; в общий репозиторий реальные данные клиентов не добавляются.

## Договорённости для интерпретации результатов

- Заказ после округления **не возрастает** при увеличении доступных остатков/своевременных поставок. Строгое уменьшение на каждую единицу невозможно из-за упаковки и MOQ. Проверяем также неокруглённую потребность и границу нуля.
- E06 не считает поставку через год покрытием потребности ближайших 10 дней. Для просроченных и частично прибывших поставок нужна явная бизнес-политика; ручные сценарии вынесены отдельно.
- A06/A07 требуют сохранения утверждённого решения или его версии при пересчёте/перезапуске. Новая рекомендация допустима, но она не должна уничтожать существующий заказ. Если появится версионирование, тест следует адаптировать к API истории, сохранив это требование.
- A08 допускает некорректный черновик, если утверждение блокируется. Разрешённые исключения из MOQ требуют отдельного описанного процесса; сейчас такого процесса нет.
- A10 проверяет трактовку карточки «Units to order» как суммы окончательных количеств. Если продукт показывает отдельно исходную рекомендацию и итог закупщика, тест должен проверять итоговую карточку, а не сумму рекомендаций.
- E17 — приёмочный тест качества: при истории зимнего уровня 165 и прочего уровня 100 ожидаем перед ноябрём хотя бы 130/день. Это выбранный допуск, не требование точного восстановления коэффициента по одному году. Проверка статистической точности требует отдельного backtest.
- E15 агрегирует одну закупку по клиенту/товару/складу/дню. Повторные поставки тому же клиенту требуют отдельного решения о регулярности. Нельзя удалять все большие заказы только по величине.
- Тесты связаны с текущими Python/API-контрактами. При переносе импорта или появлении версий заказов менять адаптер теста, а не бизнес-ожидание.

## Ограничения

Это независимый набор приёмки, а не доказательство отсутствия всех ошибок. Браузерные сценарии, нагрузка, одновременные действия закупщиков и Docker проверяются отдельно. Отсутствие Docker на машине или невыполненный ручной пункт не считается успешной проверкой. Тесты не исправляют известные противоречия исходного EKT-датасета и не подгоняют прогноз под скрытые константы генератора.
