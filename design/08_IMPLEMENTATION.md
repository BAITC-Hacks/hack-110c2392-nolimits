# План внедрения для команды и ИИ

## Перед каждым изменением

По требованию пользователя сначала `git fetch origin`, проверить `git status`, сравнить HEAD с последней `origin/main` и интегрировать актуальную основу, сохраняя чужую работу. Правила в `../CONTRIBUTING.md`. Не заменять рабочую БД демонстрационной при обновлении кода. Участников трое; ниже предлагаемые зоны ответственности, не назначение реальным людям.

Сначала изучить актуальные `frontend/src/App.tsx`, `api.ts`, `types.ts`, стили и backend schema. База первичного аудита — 402426a; 9fb5234 добавил экстремальный тестовый набор; f02f92f исправил мобильный layout. Не возвращать исправленные баги при переносе дизайна. Если код изменился после документа, актуализировать карту функций до редактирования.

## Этапы и критерии перехода

| Этап | Результат | Можно переходить, когда |
|---|---|---|
| 0. Инвентаризация | Список существующих сценариев и контрактов, владельцы файлов | Все текущие действия сопоставлены с новым экраном |
| 1. Основа | Токены, типографика, AppShell, кнопки/поля, адаптивная навигация | 320–1440 px, клавиатура и контраст проверены |
| 2. План | Четыре KPI, единый список, фильтры, карточки mobile | Тот же API выдаёт те же числа, фильтры работают |
| 3. Карточка | Расчёт, график, безопасная правка, состояния запросов | Нет старой аналитики при смене SKU; ошибки не теряют ввод |
| 4. Данные/исключения | Реестр, фактический отчёт импорта, полный список исключений | Все 5 источников и книга импортируются как раньше |
| 5. Серверные расширения | preview/commit, версии, scoped export, provenance | Контрактные тесты и UI ошибок согласованы |
| 6. Полировка | QA сценариев, пустые состояния, адаптивность, тексты | Критерии 09 выполнены и ограничения записаны |
| 7. Развитие | История, политики, сценарии | Подтверждена потребность пользователей и готов API |

Не переписывать алгоритм прогнозирования в одном коммите со стилями. Если новый экран требует изменённой бизнес-логики, сделать отдельную задачу с входами/выходами и тестами. Переход на новые единицы/округления должен иметь серверный источник истины.

## Предлагаемая структура React

```text
src/
  app/                 AppShell, routes, providers
  components/ui/       Button, Field, Badge, Alert, Dialog, EmptyState
  components/data/     DataTable, MoneyValue, QuantityValue, SourceContext
  features/procurement/ ProcurementPage, Filters, OrderRow, OrderCard, SelectionBar
  features/detail/     DetailDialog, CalculationTrace, DemandChart, AdjustmentForm
  features/imports/    DataPage, ImportDialog, ImportReport
  features/exceptions/ ExceptionsPage, ExceptionDetails
  services/            API adapter, request cancellation, DTO mapping
  styles/              semantic tokens, base, component styles
```

Это целевая структура, не требование создать десятки пустых файлов. Извлекать компоненты по мере переноса. Не вводить глобальный CSS для всех `td`/`button`, влияющий на несвязанные экраны. Прототип — визуальный ориентир, его DOM rendering не заменяет React архитектуру.

Состояние сервера отдельно от состояния представления. Query keys включают dataset/run/filters. Черновик поля живёт в форме, обновлённый ответ сервера — в кэше. Сортировка null и стабильные row IDs централизованы. Не создавать второй скрытый экземпляр формы для мобильного вида.

## Совместная работа

Предлагаемые потоки: A — UI shell/компоненты/план; B — backend contracts/импорт/версии; C — сценарии, интеграция/QA/аналитика. Перед началом согласовать занятые файлы. Один владелец токенов, api adapter и общих типов на конкретный промежуток; остальные согласуют изменения контрактом. Не считать этот текст поручением другим людям или ИИ отправлять сообщения.

Каждый коммит имеет узкую цель, список ручных проверок и ограничения. Добавлять конкретные файлы, не `git add .`. Перед интеграцией повторить fetch. Не перезаписывать рабочую ветку другого участника, не force-push. Пакет дизайна коммитить отдельно от исправлений production.

## Проверки

Frontend: TypeScript build и production build; затронутые пользовательские сценарии в браузере. Проверять mobile, tablet и desktop. Backend тесты запускать на изолированной временной SQLite, не на базе работающего сервера. Предыдущий параллельный запуск с общей SQLite приводил к конфликтам UNIQUE; это причина изоляции, а не flaky исключение для игнорирования.

Осмысленные автоматические тесты: отмена позднего ответа аналитики; 409 не затирает ввод; null price отличается от zero; экспорт не включает скрытые строки; dirty закрытие; преобразование и границы количества. Не писать snapshot-тест на каждую декоративную обёртку.

Rollback: сохранять коммиты небольшими; возвращать конкретный коммит через revert. Миграции БД отдельно с обратимостью/резервированием; UI rollback сам по себе не откатывает данные. Для постепенной выкладки допустим feature flag без двух расходящихся алгоритмов.

## Готовый стартовый запрос другому ИИ

> Обнови информацию об origin/main и безопасно интегрируй актуальную основу. Прочитай design/README.md, DECISIONS.md и спецификацию выбранного экрана. Реализуй этап [номер] в существующем React-проекте, сохрани текущие API-сценарии. Не изображай отсутствующие backend-функции готовыми. Согласуй файлы с параллельными участниками, не включай их изменения в коммит. Проверь затронутые состояния, мобильные размеры и сборку; сообщи фактические проверки, ограничения и хеш коммита.
