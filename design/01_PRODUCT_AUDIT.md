# Продукт, задачи пользователя и аудит

## 1. Обещание продукта

«Помочь закупщику сформировать обоснованный заказ, увидеть дефицит и проверить данные до утверждения». Интерфейс должен уменьшать число ручных сверок и делать последствия решения понятными. Успех — правильно проверенный заказ, а не количество карточек или графиков.

Основной пользователь: менеджер закупа, ежедневно работающий с длинными наименованиями, артикулами, упаковками, резервами и разными датами поставок. Он должен быстро отличать «нужно заказать» от «данных недостаточно». Предполагаемый контекст — ноутбук 1366×768 либо монитор 1440–1920 px. Эти параметры — проектная гипотеза, не результат исследования реальных пользователей.

Вторичные роли, предлагаемые после MVP: руководитель закупок (проверка суммы и утверждение), аналитик (политики и качество), наблюдатель (просмотр). Ролевая модель в текущем API не реализована; нельзя рисовать вымышленные аватары ответственных как существующий доступ.

## 2. Задачи и измеримые критерии

| Задача | Пользовательский вопрос | Предлагаемый критерий исследования |
|---|---|---|
| Определить приоритет | Где потребуется действие сегодня? | Найти критичную позицию и причину за 30 секунд |
| Проверить число | Почему 70, а не 65? | Найти формулу, округление и источник за 2 действия |
| Исправить решение | Могу ли я заказать 80? | Сохранить правку и увидеть её последствия без потери контекста |
| Подготовить заказ | Что уйдёт поставщику? | До скачивания видны состав, версия, сумма и единицы |
| Разобрать импорт | Почему часть файлов не подошла? | Найти строку ошибки и способ исправления без чтения логов |

Это цели будущих проверок, не измеренные результаты. Для исследования: 3–5 представителей закупа, сценарии на синтетических данных, фиксация ошибок/времени/непонятных терминов, затем корректировка.

## 3. Наблюдения по существующей реализации

Основа: просмотр работающего UI и исходников на `402426a`; при начале разработки повторить аудит актуального HEAD.

| Наблюдение | Источник | Последствие | Решение |
|---|---|---|---|
| Hero и декоративная орбита занимают значительную высоту | `App.tsx`, `styles.css` | Таблица уходит за первый экран | Убрать hero; компактный заголовок и три метрики |
| В интерфейсе смешаны английский и русский | `App.tsx` | Термины требуют лишнего перевода | Русский словарь, вынесенные строки |
| Многие подписи 9–11 px и светло-серые | `styles.css` | На ноутбуке трудно читать | Основной текст 14 px, вспомогательный 12 px, контрастные токены |
| «Live data» показывает текущую дату браузера | `App.tsx` | Создаёт ложное впечатление свежести данных | Дата среза и расчёта из метаданных; если их нет — «не указана» |
| Кнопка ekt.kz названа реальными данными | `README.md`, `App.tsx`; противоположное в `README_DATASET.md` | Неясное происхождение | «Отраслевой демонабор», постоянная метка синтетики |
| KPI остаются общими, таблица фильтруется локально | `Overview`, `visibleRows` | Числа визуально относятся к разным выборкам | Метрики текущего вида + явный общий счётчик |
| Lowest cover использует общий сортировщик по убыванию | `visibleRows` | Низкое покрытие может оказаться внизу | Явное направление для каждой сортировки |
| Экспорт всегда возвращает весь список | `api.ts`, backend export endpoint | Фильтр в UI не определяет состав файла | Диалог состава и серверный scope; до него подпись «весь расчёт» |
| Единица отображается как `u` | `App.tsx`, нет поля unit в Recommendation | Метры и штуки неразличимы | Явная базовая/закупочная единица из нового контракта |
| Поставщик показывается карточками после большой таблицы | `SupplierGroups` | Дублирование и трудно найти пакет | Вкладка «По поставщикам» на том же уровне |
| У drawer нет полного клавиатурного контракта | `Detail` | Неочевидное закрытие и возврат фокуса | Dialog, Escape, удержание и возврат фокуса |
| Ошибки правки/утверждения не показаны рядом с действием | `Detail.save/approve` | Неясно, сохранено ли изменение | Inline ошибка, retry, неизменный статус до ответа сервера |
| Аналитика может оставаться от предыдущего выбранного SKU | `openSku` | Чужой график в карточке | Сброс/ключ запроса `(run, sku, warehouse)` и loading-state |
| Редактирование количества не сбрасывается при замене row | `Detail useState` | Риск правки другого товара старым значением | Локальный draft привязан к ID и версии |
| «Engine online» статичен | sidebar | Не отражает сбой API | Проверенный индикатор связи с отдельным last-success |

Не все эти проблемы требуют нового backend. Изменение visual CSS само по себе их не решает.

## 4. Радикальное изменение композиции

Старая структура: декоративный ввод → семь KPI → длинная таблица → дубли поставщиков.

Новая структура: контекст данных и расчёта → компактные actionable-метрики → рабочая очередь с сохранённым видом → объяснение выбранной позиции → просмотр пакета поставщика. Импорт и проблемы данных получают самостоятельные страницы с понятным результатом действий.

Сохранить: бренд StockPilot, объяснимость, таблицу рекомендаций, доступ к данным и аномалиям. Заменить: визуальный язык, иерархию, терминологию, работу со статусами, взаимодействие таблицы и карточки, поток импорта и экспорта.

## 5. Что не делать

Не превращать инструмент в лендинг, не добавлять фоновые фотографии склада, глобус поставок без геоданных, чат вместо таблицы, неоновые градиенты, стеклянные карточки, счётчики «AI confidence 98%» без калиброванной модели. Не добавлять выдуманные финансовые эффекты. Вау-эффект должен давать ясное объяснение трудного решения.
